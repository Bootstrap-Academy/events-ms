# Retained Events rollout prerequisites

Coordinate Events activation with the application writer hold and recovery procedure. Verify the selected compatible backend and service releases before admitting new writers.

Stop and drain every older Events booking, cancellation, confirmation, cleanup and unkeyed XP worker before applying the new schema or admitting new protocol writers. An old unguarded booking writer can evade the subject reservation header; an old unkeyed XP worker can issue an award for a newly marked booking/session outside the new receipt protocol. Deploy the compatible API and worker set together. Do not run an old writer against the new earning/erasure state during rollout or rollback.

Apply the complete migration chain. Existing booking/session XP markers and existing subject reservation headers remain NULL. No migration or startup repair may infer historical nonpayment from an empty journal, stamp old sessions as new, or recreate an erased subject. Legacy review obligations must remain available for evidenced resolution. A new participant marker does not authorize a legacy instructor award.

The configured `pool_size + max_overflow` is the total Events connection allowance. Startup reserves one slot from that existing allowance for committed availability reads: one read connection, zero read overflow, three-second checkout deadline and five-second read deadline. The general pool receives the remainder. For example, the default 20 + 20 allowance becomes general20 + overflow19 plus reader1, still40. A finite allowance of at least two is required; startup rejects total1 or an unbounded pool instead of silently increasing the deployment cap. Read queries take no owner-row locks and never call into the general pool. Availability witness insertion keeps its existing postcommit general-pool path. Shutdown first cancels/awaits all three workers, then disposes both pools.

When recovering or restoring a snapshot, reconcile the newer original contract/payment identities, current recipient grants and withdrawals, canonical erasure receipts, subject reservation headers, earning provenance, immutable requests and committed outcome observations before releasing writers. Preserve newer erasure/earning evidence during recovery; do not make a missing older row mean “not erased” or “award never applied.” An uncertain remote effect cannot be replaced with a fresh operation merely to resume service. Keep original financial ownership separate from the current service recipient.

Before admitting writers, verify the paired service routes and configured authentication, booking/cancellation receipts, original-document and owner exports, and benefit delivery/retention. Publish compatible interfaces and document versions together. Record the actual rollout and recovery observations separately; a successful build or synthetic control does not establish delivery, payment or a completed restore.
